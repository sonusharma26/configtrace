# Release checklist

Everything in this checklist is pending unless subsequently checked by a maintainer with actual evidence. v0.1 is an implementation milestone inside this v0.2 source tree, not an independently published or validated release.

## Before calling v0.1 usable

- [ ] Install dependencies and inspect the generated lockfile.
- [ ] Compile the package and resolve actual type/compiler errors.
- [ ] Run the focused test suite and retain results.
- [ ] Confirm startup/read/write/delete/missing/empty semantics using synthetic fixtures.
- [ ] Explain a stale inherited value without claiming parent-shell history.
- [ ] Confirm supported dotenv calls are delegated once and preserve application behavior.
- [ ] Compare deliberate pairs and reject unpaired value equality.
- [ ] Confirm raw canaries never enter recorder artifacts or its diagnostic messages.
- [ ] Preserve application output, nonzero exit and signal behavior within a named tested target.
- [ ] Confirm truncation/failure cannot be labeled successful universal coverage.

## Before calling v0.2 usable

- [ ] Check source-map attribution against the original fixture line.
- [ ] Exercise opted-in direct Node children, caps, explicit envs, fork inheritance and missing child streams.
- [ ] Exercise unsupported Worker/native/original-reference paths and retain truthful notices.
- [ ] Validate change-and-change-back sequence comparisons.
- [ ] Validate jointly exported versus independently exported domains.
- [ ] Review metadata minimization, canaries and key-file exclusion.
- [ ] Review the HTML in at least two browsers, including narrow layout and CSP.
- [ ] Exercise hostile artifact/policy inputs and confirm bounded handling.
- [ ] Validate local adapter setup/cleanup/failure behavior without leaking raw exceptions.
- [ ] Publish exact tested Node/OS/dotenv combinations; retain failures and gaps.
- [ ] Record named-fixture overhead without generalized performance claims.
- [ ] Obtain evidence of usefulness on three realistic debugging cases.

## Before publishing to a registry or public repository

- [ ] Choose a repository and configure a private security-reporting channel.
- [ ] Check the working name `configtrace` for registry availability and naming conflicts; none is asserted here.
- [ ] Replace `private: true` only after making an intentional publication decision.
- [ ] Populate repository, homepage, author/maintainer and bugs fields with real values.
- [ ] Review the MIT license and dependency license obligations.
- [ ] Audit the dependency graph and pin reviewed resolutions via the real lockfile.
- [ ] Choose and test the required supported Node versions and operating systems.
- [ ] Build distributable files in an authorized release environment.
- [ ] Inspect the package contents before publishing; exclude keys, traces, fixtures containing real data and temporary sessions.
- [ ] Smoke-install the packed artifact into a clean project; verify CLI and library exports.
- [ ] Set registry authentication/2FA/provenance according to the actual publication workflow.
- [ ] Add a synthetic demo recording without real environment values or local private paths.
- [ ] Replace “unvalidated source” statements only with specific completed results.
- [ ] Tag the actual validated source commit and document known limitations alongside the release.

No registry release, package upload, GitHub push, CI run or deployment was performed as part of this delivery.
